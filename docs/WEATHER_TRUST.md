# Weather trust and advertising safety

Forecast freshness uses an injectable wall clock (`ForecastScreen.clock`, default `DateTime.now`). Observations are never moved forward to make demonstration or cached data appear fresh. Observation time (`sourceUpdatedAt` / `lastUpdated`) and retrieval time (`fetchedAt`) survive cache serialization independently. A cache fallback is explicitly marked offline. Future or missing observation times are unavailable for safety eligibility; observations older than 30 minutes are stale.

The screen reevaluates elapsed time each foreground minute and immediately on app resume. Background timers do not request weather. Resume invalidates previously clear safety coverage when a refresh is needed; a fresh return from an ad or share sheet does not request weather again. Each weather request has an identity, so a delayed response from the previous selected location cannot replace the current forecast or safety state. Advertising observes weather state; it does not request weather.

Temperature storage remains Celsius in weather models. Current, feels-like, hourly, daily, metric chips, and generated roast display tokens convert to the selected Fahrenheit/Celsius preference. Roast selection thresholds continue using Fahrenheit; historical quoted sample roasts retain their original text and sample labels.

Minute precipitation only claims the next hour when valid, continuous one-minute samples cover the entire horizon from the real current time. Empty, old, future-only, missing-value, duplicated, gapped, and truncated samples report unavailable or partial coverage. Rain timing is calculated from timestamps, not array positions. The legacy compatibility numeric probability is accompanied by `precipitationChanceKnown`, preventing absent provider probabilities from displaying as zero rain. Missing last-hour precipitation is unavailable, not “None.”

Official warnings precede current conditions, comedy, and advertisements. Relevant warnings suppress the Forecast roast. Source, area, start, expiry, instructions, and description remain available in Flutter text. The shared `WeatherSafetyBanner` provides compact access from other screens without covering navigation; its details sheet reports its modal state to monetization. New warnings expand the summary again. Expired alerts are excluded; an alert with missing expiry remains relevant conservatively.

`WeatherLocationController.safetyStatus` is one of `unknown`, `stale`, `clear`, or `activeAlert`. A clear state requires explicit provider coverage, a check no more than 10 minutes old, a current observation no more than 30 minutes old, matching selected/requested coordinates, and no offline fallback. Empty alert arrays from legacy endpoints do not prove no warnings. `activeAlerts` retains received warning text when an update fails. Every advertising opportunity must recheck the live getter.

The bundled backend only attests coverage when its upstream response explicitly includes an alert array; fallback and absent-alert paths remain unknown. Existing deployed backends without the new marker therefore suppress advertising until verified coverage exists. Backend source changes are included but **not deployed** by this task. This conservative gate is intentional and must not be replaced with an “empty means clear” default.

Verification includes 14 weather trust regression tests, the existing weather/location/forecast/summary and roast suites (41 combined tests), and 16 backend tests. Cases include old/future timestamps, offline retrieval, resume aging, late old-location responses, C/F conversion and roast tokens, precipitation gaps, warning precedence, and a 320px warning banner at 1.8× text scale.
